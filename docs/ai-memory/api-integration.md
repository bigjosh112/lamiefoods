# API Integration — contract catalog + client pattern

> The single source of truth for every backend endpoint this app consumes, plus the
> canonical pattern for consuming them. Populated by the `consume-endpoint` skill.
>
> **The iron rule: contracts are recorded, never invented.** Every entry cites its
> evidence — backend source code, a screenshot from the backend platform, an API doc,
> or a real captured response. If a field's type or optionality is unknown, it stays
> marked `UNKNOWN — ask backend` until confirmed. No guessed shapes, ever.


## PENDING — what checkout needs from the backend

> Added 2026-09-06. **Nothing below is a contract.** These are the open questions
> the frontend cannot answer for itself. No endpoint has been recorded, so no
> endpoint has been implemented: `/checkout` validates the customer's details and
> then says plainly that payment is not connected. It does not POST anywhere.

The form already produces `CustomerDetails` from `@lamiefoods/types`
(`fullName`, `email`, `phone` as `+234…`, `deliveryAddress{addressLine, landmark,
city, state}`), so if the backend accepts that shape, no reshaping is needed.

Questions for the backend developer:

1. **Create-order endpoint** — method, path, request body, response. Does it take
   the cart lines, and in what shape? Our lines are `{slug, pack, quantity}` and
   prices are integer **kobo**.
2. **Who owns pricing?** The frontend currently holds placeholder prices in
   `content/products.ts`. Prices must come from the server before launch —
   client-held prices are trivially tampered with, and the server must price the
   order itself regardless of what the browser sends.
3. **Delivery fee** — how is it calculated, and at what point? The UI says
   "confirmed before payment is taken", which needs an endpoint that takes an
   address and returns a fee.
4. **Paystack flow** — does the backend initialise the transaction and return an
   authorization URL / access code, or does the frontend call Paystack inline
   with the public key? Verification must happen server-side either way.
5. **Order reference** — generated by the backend? Returned when?
6. **Error envelope** — the shape of validation and payment failures, so the form
   can surface field-level errors from the server.
7. **Stock** — is availability checked at order time? What does an out-of-stock
   response look like?
8. **Sales ranking** — is there an endpoint, or a field on the product, that says
   how much of each product has actually sold? The landing badge is a status:
   every product currently reads "New" because the brand has not launched. The
   owner wants a **"Best seller"** badge once records exist, and that badge is a
   claim about what other customers bought. It must be driven by real order data
   — inventing it would be inventing social proof, which is the same failure as
   a fabricated review. Nothing renders it until this is answered.

Until 1–8 are answered, `apps/web/src/lib/api` stays endpoint-free by design.

## Canonical consumption pattern

Every endpoint is consumed in three layers, in this order. Follow the shapes of the
first implemented endpoint in this repo; if none exists yet, establish them from this
template.

1. **Typed client function** — `<src/api/<resource>.(ts|js)>`
   One function per endpoint. Owns: URL building, method, headers, serialization,
   throwing a typed error on non-2xx. Owns nothing about React.
2. **Hook** — `<src/hooks/use<Resource>.(ts|js)>`
   Wraps the client function. Owns: loading/error/data state, cancellation/stale
   guards, cache or refetch policy. Returns `{ data, error, isLoading, <actions> }`.
3. **UI states** — every consuming component renders **all four**:
   loading (skeleton/spinner), error (message + retry), empty (real empty-state, not
   a blank screen), success. A PR that adds an endpoint without all four is incomplete.
